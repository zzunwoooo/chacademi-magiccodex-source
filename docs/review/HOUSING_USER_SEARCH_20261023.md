# Housing user search — prepared, not deployed

The popup title and buttons are exactly 유저 검색. The upper rectangle is a text input. Outer popup remains 540x720 at the existing anchor; other menus, inventory and room style are unchanged. Results use server SQL search and 30-row pages, ranked online friend → online nonfriend → offline friend → offline nonfriend. Stable UUID is the primary key. Only records from real configured nickname domains participate; no Mojang/random account lookup or creation occurs. The same global read-only nickname federation from 3982c573 is retained.

Operational nickname and friend sources are SELECT-only (SQLite URI mode=ro/open_mode=65/query_only, MariaDB read-only connection). A derived in-memory SQLite index is refreshed at most once per 5 seconds on Housing DB worker; temporary tables hold the proxy UUID roster and the viewer's exact current Bridge friendships. These temporary writes never touch operational databases. SQL filters/sorts/pages before returning at most 30 records. Friendships are not unioned across independent stores, which could revive a removed edge. Central server room-entry checks enforce directed friendship, self and operator exceptions even for forged Visit packets. No room ownership, friendship, guestbook or nickname migration is performed.

The existing housing heartbeat cannot include arena because no housing plugin is installed there. A small standalone Velocity addon supplies an exact global UUID roster from school/wild/arena. Requests are accepted only from the player's active trusted backend; proxy consumes the nonce request before clients can see it. Responses are nonce/player matched and chunked to 512 UUIDs/frame. Backend safety limit is 64 simultaneous searches and 50,000 online UUIDs; over-limit/unavailable states fail explicitly rather than silently presenting partial order. This addon does not modify the existing Party/Bridge/MCPets JARs or send chat.

Client input uses 300ms debounce, monotonically increasing generations, connection/player/screen guards and explicit timeout. Server coalesces requests to the newest generation and permits only one delayed task per player. Session/quit/room transitions invalidate results. Enter retries; previous/next uses server pages. The registered nickname is shown for offline users and historical authors without rewriting saved English snapshots or body/UUID/time data.

Tests passed: Housing 16 (including 611-row server paging, ordering, offline lookup, dedupe, source conflict, read-only preservation and ACL), standalone proxy 2 (real handler with fake clients, active-source authentication and 1053-UUID chunking), client 456 (including stale-generation lifecycle). The client contract test fixture was aligned to the proven f516bb20 published UI source; no operational YAML was changed. Actual registered DB search was separately read-only verified from school/wild/arena: all 5 real registrations returned without UUID duplicates. That audit used an explicitly empty synthetic online snapshot, not live online validation.

Only baseline-preserving deployment packages are targets. School/wild packages replace HousingPlugin/HousingStore/Rooms and add only the search/identity helpers/protocol. Wild retains its absence of the school Story event. UI package preserves every old JAR entry except HousingClient/HousingScreen class family and fabric.mod.json; new search classes/protocol are added. All other resources/classes are byte-identical. Exact hashes and per-entry comparisons are in ready.json. Do not deploy full rebuilt aggregate JARs.

No install, restart, operating DB write/migration, client close/replacement or launcher publication occurred. Deployment requires school/wild Housing JARs, the new Velocity presence addon, and the bounded UI JAR. Existing friendship domains remain split; this change deliberately does not invent global friendship authority. Real multi-client visual/online validation is outstanding. Screenshot pixel materialization could not complete because the Library helper calls os.setxattr, unsupported on this Windows runtime; image metadata and existing source coordinates were available, but actual screenshot pixels were not inspected.
