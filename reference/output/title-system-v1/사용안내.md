# 칭호 설정 시스템 v1

클라이언트 모드 **0.35.0 / Minecraft 1.21.4**, 서버 플러그인 **MagicCodexBridge 0.27.0**.

접두사와 접미사를 별도로 선택하고 `접두사 + 닉네임 + 접미사`로 표시한다. 보유한 칭호만 목록에 나오며, 양쪽의 **선택 안 함**으로 각각 해제할 수 있다. 미리보기 후 적용을 누르면 서버 검증을 거쳐 즉시 저장된다. 보유 중인 칭호를 회수하면 해당 칭호의 선택도 함께 해제된다.

## 열기와 조작

- `/칭호` 또는 `/codextitles`
- 상단 메뉴의 **칭호** 아이콘 (장비 옆)
- 목록을 클릭하여 선택, 휠/스크롤바로 이동, **적용**으로 저장
- 키보드 왼쪽 화살표는 다음 접두사, 오른쪽 화살표는 다음 접미사, Enter는 적용, ESC는 닫기

PNG, 글씨와 마우스 클릭 위치는 승인된 1080×880 좌표에서 함께 축소한다. 이름은 실제 서버 닉네임 `%user_nickname%`을 기존 DisplayNames 해석기로 가져온다. 제목·이름·목록은 런타임 텍스트이고 PNG에 박혀 있지 않다. 배경에 은은한 빛의 이동과 밝기 변화가 들어간다. 긴 칭호는 글씨를 지나치게 줄이지 않고 말줄임으로 표시한다.

## 관리자 명령어

권한: `magiccodex.titles.admin` (기본 OP). 일반 사용 권한 `magiccodex.titles`는 기본 허용이다.

```text
/칭호관리 목록
/칭호관리 지급 <플레이어 계정명 또는 UUID> prefix_starlight
/칭호관리 지급 <플레이어 계정명 또는 UUID> suffix_researcher
/칭호관리 회수 <플레이어 계정명 또는 UUID> prefix_starlight
/칭호관리 확인 <플레이어 계정명 또는 UUID>
/칭호관리 리로드
```

지급/회수는 DB에 반영된 뒤 완료 메시지를 보낸다. 같은 칭호의 중복 지급은 중복 기록을 만들지 않는다. 이미 접속 기록이 있는 계정은 오프라인 계정명으로도 조회할 수 있고, UUID는 오프라인에서도 사용할 수 있다. 기본 설정에는 `학생` 접미사를 첫 접속 시 지급하며, 선택은 직접 해야 한다.

## 플레이스홀더

칭호 출력은 기존 기숙사 플레이스홀더와 충돌하지 않는 별도 확장 `chacademiatitle`에 등록한다. PlaceholderAPI가 설치되어 있어야 한다.

| 플레이스홀더 | 출력 예시 |
|---|---|
| `%chacademiatitle_full%` | 별빛을 발견한 차카 연구가 |
| `%chacademiatitle_full_colored%` | 설정한 칭호 색을 적용한 전체 이름 |
| `%chacademiatitle_prefix%` | 별빛을 발견한 |
| `%chacademiatitle_suffix%` | 연구가 |
| `%chacademiatitle_nickname%` | 차카 |
| `%chacademiatitle_prefix_id%` | prefix_starlight |
| `%chacademiatitle_suffix_id%` | suffix_researcher |

미선택 접두사/접미사는 빈 문자열이며, 전체 이름의 불필요한 공백은 제거한다. 온라인 플레이어 캐시에서 읽으므로 채팅/TAB 등의 플레이스홀더 조회마다 DB를 호출하지 않는다. 선택 저장 직후 갱신하며 닉네임은 기존 해석기의 짧은 캐시를 사용한다. 오프라인 미캐시 대상은 빈 문자열을 반환한다.

```text
/papi parse me %chacademiatitle_full%
```

## 칭호 추가와 수정

파일: `plugins/MagicCodexBridge/titles.yml`

```yaml
titles:
  prefix_starlight:
    side: prefix
    name: 별빛을 발견한
    color: '#96E4EC'
    enabled: true
    initial: false
  suffix_student:
    side: suffix
    name: 학생
    color: '#DEC58E'
    initial: true
```

- ID는 소문자 영문·숫자·`_`·`-`, 최대 48자. 표시 이름은 최대 48자, 전체 목록은 최대 96개.
- `side`는 `prefix` 또는 `suffix`, `color`는 `#RRGGBB`.
- `enabled`를 생략하면 true, `initial`을 생략하면 false.
- `initial: true`는 플레이어의 칭호 기록을 처음 만들 때만 지급한다. 이후 회수한 기본 칭호를 재접속 때 다시 지급하지 않는다.
- 설정을 수정한 뒤 `/칭호관리 리로드`로 반영한다. 표시 이름 변경은 같은 ID를 유지한다.
- 학교·야생·던전에는 같은 `titles.yml`을 배포하고 각 서버에서 리로드한다. 정의 자체는 YAML로 관리한다.

## DB와 서버 이동

기존 `plugins/MagicCodexBridge/database.properties`의 설정을 그대로 사용한다. MariaDB 모드에서는 학교·야생·던전이 같은 데이터베이스를 사용하면 칭호 보유와 선택을 공유한다. 테이블은 시작 시 자동 생성한다.

```text
codex_title_player: UUID, revision, 선택한 접두사 ID, 선택한 접미사 ID
codex_title_owned: UUID + 칭호 ID (중복 금지)
```

DB 쓰기 작업은 별도 작업 스레드에서 처리한다. UUID 행 잠금과 revision 검증으로 다른 서버/운영자 변경을 오래된 화면이 덮어쓰지 않는다. 서버 접속·창 열기에서 새 기록을 읽고 온라인 캐시는 30초 주기로 갱신한다. GUI가 열려 있으면 30초 주기로 조회해 선택 목록도 갱신한다. 기본 SQLite 모드에서는 `titles.db`로 단일 서버 테스트가 가능하다.

`database.properties`에 접속 비밀번호가 있으므로 배포 ZIP에는 이 파일을 넣지 않았다. 서버별 기존 설정을 유지한다.

## 다른 기능 연결 API

신뢰할 수 있는 서버 플러그인은 메인 스레드에서 다음 API를 사용할 수 있다. 콜백은 DB 커밋이 끝난 뒤 메인 스레드에서 실행한다.

```java
bridge.grantTitle(player.getUniqueId(), "prefix_starlight", success -> {
    // success=true이면 보유 기록이 저장됨
});
bridge.revokeTitle(player.getUniqueId(), "prefix_starlight", success -> {});
```

운영용 지급 명령어도 콘솔에서 사용할 수 있다. 클라이언트는 ID 선택 요청만 보내며 보유 여부, 접두사/접미사 구분, UI 세션, 데이터 버전은 서버가 검증한다.

## 설치

1. 서버를 종료하고 이전 MagicCodexBridge JAR 하나를 **0.27.0**으로 교체한다.
2. 처음이면 ZIP의 `설정/titles.yml`을 `plugins/MagicCodexBridge/titles.yml`에 넣는다. 파일이 없으면 플러그인이 기본 파일을 자동 생성한다.
3. 기존 설정·DB 접속 파일·저장 파일은 그대로 유지한다. 새 서버라면 함께 제공한 `기본설정-새서버용` 자료를 참고한다.
4. 학교·야생·던전에 같은 버전과 같은 칭호 정의를 적용하고 서버를 시작한다.
5. 런처 mods에는 `magic-codex-ui-0.35.0+mc1.21.4.jar` 하나만 둔다. 모드는 여전히 클라이언트 전용이다.

테스트 전용 TitleFixture는 배포 ZIP에 포함하지 않는다.

## 검증 기록

- Paper: 전체 JUnit 116개 통과 (보유 검증, 위조 ID·잘못된 칸, 선택 해제, 기본 칭호 회수, 중복 지급, 재접속, 다른 서버의 오래된 선택 거부 포함).
- Fabric: 전체 JUnit 177개 통과 (UI 크기·좌표, 클릭 간격, 긴 칭호 말줄임과 유니코드 문자 보존 포함).
- 분리된 MariaDB 두 연결: 보유·선택 공유, 회수, 위조 선택, revision 충돌, 동시 변경, 재접속 검증 통과.
- 실제 Paper + Fabric: 메뉴/명령어 진입, 닉네임, 양쪽 목록, 적용, 선택 해제, 회수, 위조 패킷 거부, 창 재열기와 플레이스홀더 검증 통과.
- 실제 게임 GUI 2·3 스크린샷과 GPU 텍스처 상태 확인.

실제 서버망 학교↔야생↔던전 이동은 운영 환경에서 최종 확인하면 된다. 공유 DB의 저장 동작은 분리된 테스트에서 검증했다.
